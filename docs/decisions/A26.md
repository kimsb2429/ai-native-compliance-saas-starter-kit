# A26 · Prompt registry by slug, revisions carry the model

## Decision
Prompts are registered by slug, with revisions stored immutably in Postgres. The table `prompt_revisions` holds the `slug`, `revision`, `model_id`, `system_text`, `user_template`, and `is_active` flag. Exactly one revision per slug is active, enforced by a partial unique index. At invocation time, the agent builder reads the active revision for the agent’s prompt slug, caches it in process memory for 60 seconds, and retains the last known good value in case the database becomes unreachable. The `model_id` in the revision is optional: when set, it can be a full Bedrock model identifier or an alias like `MODEL_SMALL` or `MODEL_MEDIUM`, resolved at runtime from environment variables, and it overrides the agent row's `model_size`; when null, the agent row decides. Updating a prompt or changing the model requires inserting a new revision and flipping the `is_active` flag, which takes effect without redeploying the agent image. This allows prompt changes and model swaps to propagate immediately across all agent invocations without touching infrastructure or code.

## Alternatives considered
- Inline prompts in agent code
- Loading prompts from a directory in the git repository at import time
- Using Amazon Bedrock Prompt Management
- A separate HTTP service for prompt resolution (as used in the engagement)
- A full inference gateway that proxies all model traffic

## Why this form won for the kit
The agent definitions are already stored in Postgres as database rows (decision A3), so extending the schema to include prompts and revisions adds no new dependencies. The runtime already queries the database on every invoke to load the agent definition, so fetching the prompt revision is a natural extension of that flow. This keeps the hot path contained and avoids introducing network hops or external services. Bedrock Prompt Management was rejected because passing a prompt ARN as the model ID prevents setting system prompts and tools directly in the Converse API call, which breaks how the Strands SDK constructs agents. Even if used, it would still require a remote call per invoke, so it offers no reliability or performance benefit over a local database read. The cache in `agent/prompts.py` limits database load, and the fallback mechanism ensures continuity if the database is temporarily unavailable.

## Tradeoff
This design removes code review from the prompt change process unless the team chooses to implement a separate workflow. A malformed or harmful prompt can go live instantly with no gate. The registry is not reusable outside this platform, unlike a shared service. The in-process cache means changes may take up to 60 seconds to appear in active sessions, depending on cache TTL and invocation frequency.

## In the engagement
The prompt system was not part of the agent at all. Each node in a fixed execution graph made an HTTP GET request to a service called the "GenAI proxy" to retrieve its system prompt and model ID by slug. The service authenticated each request with a short-lived JWT and returned the active revision. The node then called Bedrock directly using the returned model ID. The service also delivered guardrail instructions as reusable text fragments injected into prompts. Three factors made HTTP the right shape in that context. First, consumers spanned multiple languages and networks: Python agents on AgentCore, a Node.js service, a studio UI for authors, and a product backend that used a fetch-and-run endpoint. They could not all maintain a shared database connection, so HTTP was the only universal interface. Second, prompt authors were not the engineers maintaining the agent codebase; they needed a dedicated editing interface, authentication, and revision history without requiring pull requests. Third, the same prompts were used across different model providers, including OpenAI and Alibaba, so a Bedrock-only solution could not support the full scope. None of these conditions apply in this kit. The platform is single-language, single-deployment, single-provider, and authoring is done directly in the database. If any of those conditions return, the escape hatch is a thin HTTP read API over the same Postgres table, preserving the schema.

## Guardrails: instruction text versus an enforced control
Including guardrail text in the prompt is a suggestion only. The model can ignore it, there is no enforcement on output, and prompt injection can overwrite or bypass it. The kit uses an Amazon Bedrock Guardrail configured with content filters, PII detection and anonymization for email, phone, and US SSN, and a blocked topic for "regulatory evasion". This guardrail is wired into every model call through the Strands `BedrockModel` guardrail settings. Bedrock evaluates both input and output, applies masking or blocking, and returns intervention metadata. This is observable in flow 05, where a request containing PII and a regulatory evasion attempt is intercepted. Two things I learned wiring it: a denied-topic definition has to be narrow (the first draft, "hide, falsify, backdate, or evade required regulatory reporting", also blocked honest questions about deadlines and evidence), and on a tool-result turn Bedrock evaluates the system prompt as input unless only the user message is wrapped as guard content, which is why the model is built with guardrail_latest_message on; without it, "You are a compliance gap checker" tripped the prompt-attack filter. Prompt text remains appropriate for tone, format, and task framing. The guardrail is the enforced control. In the engagement, the account had a guardrail resource in draft state that was never activated in any model call.
