# B14 · Pooled multi-tenancy, enforced by Postgres

## Decision
One AgentCore runtime serves all tenants from a single container image. Tenant identity is derived from the Cognito ID token, which AgentCore validates at the edge via a custom JWT authorizer. The agent code then revalidates the token in process, checking the signature against the JWKS endpoint, the issuer, and the audience. The `custom:org_id` claim is extracted and stored in a ContextVar that persists for the duration of the invocation. The request body cannot specify or override the tenant. The database uses a single psycopg connection pool with a minimum of one and a maximum of ten connections. Before any tenant-scoped operation, the transaction sets `app.org_id` using `set_config('app.org_id', <uuid>, true)`, which is transaction-local and automatically cleared. Row-level security policies on tables like `documents` and `obligations` filter data based on this setting. `FORCE ROW LEVEL SECURITY` ensures even the table owner is subject to these policies. The runtime connects to Postgres as `kit_app`, a LOGIN role with `NOBYPASSRLS`, preventing it from bypassing RLS. Tools are bound to the tenant at build time by closing over the org ID, since Strands may execute tools on worker threads where ContextVar is not propagated. Flow 03 demonstrates isolation: tenant B asks about tenant A’s permit by name and receives no results from A’s data.

## Alternatives considered
- One runtime and one database role per tenant (silo model)
- One shared pool with no tenant context or keying
- A new database connection per request
- Pooled compute with per-request AWS credentials using STS session tags and ABAC (the AWS standard for pooled SaaS, marked as the next step but not implemented)

## Why pooled won
Pooled multi-tenancy was chosen for density and onboarding speed. A new tenant requires only a Cognito user with a `custom:org_id` attribute and corresponding rows in the database; no deployment, no infrastructure change. This aligns with the AWS pool model. The engagement’s original approach was unorthodox due to three key gaps: trust in request body for tenant, application-level isolation without RLS, and broad IAM permissions. This kit fixes each while preserving the efficiency of pooling.

## Tradeoff
The shared 10-connection pool and single runtime create a noisy neighbor risk and a single crash domain across tenants. The runtime’s AWS IAM role remains tenant-agnostic, meaning there is no IAM-level backstop for cross-tenant access to AWS resources like S3 or SSM. That control is deferred to phase two, which would use STS session tags per invoke with S3 prefix conditions. AgentCore does not enforce tenant ownership of session IDs, so clients must avoid reusing sessions across tenants. There is no RDS Proxy or PgBouncer; transaction-scoped `set_config` would pin sessions on such proxies, so the kit connects directly to Neon Postgres. One consequence of a serverless database that suspends when idle: a warm pool holds dead sockets after a resume, and the first deployed run of flow 03 failed with an SSL EOF until the pool was set to validate connections on checkout and retry once.

## In the engagement
The platform used one runtime for all tenants. Tenant context (company, business, site, user) was taken from the request body and trusted without JWT verification. Database routing used a dictionary of asyncpg pools keyed by infrastructure prefix, not tenant. Data isolation was enforced only in application code. The execution role had broad access: shared S3 prefixes, full SSM config tree, and `InvokeModel` on all models with no tenant conditions. The engagement’s own architecture notes named per-request scoped AWS credentials as the lever, with the first contractual isolation requirement as the trigger.

## In this kit: the three fixes
- Tenant identity comes from a verified JWT claim (`custom:org_id`), not the request body. AgentCore uses a custom JWT authorizer pointing to the Cognito discovery URL, and the agent revalidates the token in process.
- One connection pool replaces multiple pools. Postgres RLS, driven by transaction-local `set_config`, replaces app-level scoping.
- The runtime now uses `kit_app`, a non-superuser database role with `NOBYPASSRLS`, ensuring it cannot bypass RLS policies.
