# A3 · Agents as rows, built per invoke

## Decision
An agent is a row in the agent_definitions table. Each row holds agent_ref, environment, version, model_size, prompt_slug, tools as a JSON list, structured_output, and is_active. One container image serves all agents. On every invocation, the runtime reads the active row for the requested agent_ref and environment, resolves the prompt_slug through the prompt registry, binds the named tools to the calling tenant, and constructs a live Strands Agent. Adding an agent requires one INSERT statement. Updating its tool set or default model size is a row update; a prompt revision can also carry a model and override the row. No redeploy is needed.

## Alternatives considered
(1) One deployed runtime per agent, each with its own container image, IAM role, and deployment pipeline.
(2) Agent configuration baked into the container image at build time, with prompts and tools compiled into the code.
(3) A hard-coded agent registry implemented directly in Python, with no external configuration source.

## Why it won
This design supports SaaS scale with minimal operational cost. The platform we built was expected to grow to dozens of agents across tenants, and a separate deployment per agent would have made iteration slow and expensive. Product decisions like changing a prompt or swapping a model must not require engineering involvement or a new release. Storing definitions in Postgres enables that. It also provides versioning by default: environment and version are first-class fields, so dev, stage, and prod variants coexist as rows.

## Tradeoff
The definition read occurs on every invoke path, making Postgres a required dependency even for cold starts. If the database is unreachable, the invoke fails with a "database unavailable" error; a missing or inactive row fails with "Agent not found". A live invoke in the demo account showed the second case and confirmed the hot-path dependency. A malformed row fails at runtime, not in CI. The kit reduces this risk with a check constraint on model_size, a foreign key from prompt_slug to the prompts table, and a unique partial index ensuring only one active row per agent_ref and environment. The entrypoint also grows in complexity because it must safely resolve and validate configuration on every call.

## In the engagement
The platform used this pattern as its core architecture. Agent definitions included additional fields like skills, plugins, and agent type (simple or graph), all stored in Postgres. A qualifier-to-environment map controlled which definition was active where. The builder constructed either a flat agent or a Strands graph based on the row. A live invoke in the demo account, with no Postgres reachable, failed immediately with "Agent not found (env=prod)", proving the dependency.

## In this kit
The structure is simplified to what a starter kit needs. There are no graph agents, plugins, or skills. Tools are two static functions. Structured output uses one Pydantic schema. The core idea remains: agents are rows, built on demand. The same mitigation lever exists (caching or snapshotting definitions to remove the DB from the cold path) but the kit leaves the dependency visible for clarity.
