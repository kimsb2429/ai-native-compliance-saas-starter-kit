# flow 01 · A3 · intake extract obligations

## What you send

I sent a request as acme-user using the payload file examples/payloads/01-intake-extract-obligations.json.

```json
{
  "agent_ref": "obligation-extractor",
  "document_id": null
}
```

## What runs

1. scripts/invoke.py signs in acme-user to Cognito and gets an ID token carrying custom:org_id
2. POST to the runtime with the bearer token, a new session id, and the payload {agent_ref: obligation-extractor, document_id: null} (null = the tenant's most recent document)
3. AgentCore validates the token at the edge; agent/main.py verifies it again and sets the tenant ContextVar
4. agent/builder.py loads the obligation-extractor row: model_size medium (Nova Pro), prompt slug obligation-extractor-system, no tools, structured_output ObligationList
5. agent/extract.py loads Acme's most recent document inside a tenant transaction (RLS), renders the registry's user template around the document text, and asks the model for an ObligationList (Strands forces a tool call shaped like the schema)
6. the rows are written back inside a tenant transaction: existing obligations for that document are deleted, then one row per extracted obligation is inserted with org_id = Acme
7. the runtime returns one JSON object: document_id, title, obligations (the parsed list), count, stop_reason

## What it proves

A3 is demonstrated: the obligation extractor is defined as a database row with a reference to a prompt slug and a structured output schema. No code change or container rebuild was needed. The same running image used for chat agents instantiated this extraction flow. The domain model lives in the schema definition (agent/models.py), which drives both validation and persistence.
